Start with [Quickstart](/quickstart) to use one stable source URL and one
ReasonBlocks key with your existing Anthropic or OpenAI client. This reference
also covers the optional `rbtrace==1.3.1` helper and native Bedrock integration.
Version `1.3.0` and existing generated helpers remain compatible. Version `1.3.1`
adds dispatch diagnostics without requiring new URLs, keys or client setup.

## `Connection(source_id, api_key=None)`

Resolve a source's authenticated endpoints without assembling provider URLs.
By default, the server credential comes from `REASONBLOCKS_API_KEY`.

```python
from rbtrace import Connection

rb = Connection(source_id="SOURCE_ID")
```

| Method | Purpose |
| --- | --- |
| `rb.client_kwargs("anthropic")` | Settings for Anthropic or AsyncAnthropic |
| `rb.client_kwargs("openai")` | Settings for OpenAI or AsyncOpenAI |
| `rb.client_kwargs("gemini")` | Settings for `google.genai.Client` |
| `rb.instrument_bedrock(client, serving=True)` | Instrument an existing boto3 Bedrock client without changing IAM authentication; allow an approved nonstreaming rollout |
| `rb.run(task_id, snapshot_id=None)` | One top-level user turn, including its tool loop and final answer; use a new ID for the next turn |
| `rb.status()` | Read remote recording and training-eligibility status |
| `rb.diagnostics()` | Inspect local SDK delivery information |

`serving=False` keeps native Bedrock in capture-only mode. Streaming operations
always stay upstream. An unknown candidate outcome is not silently replayed
against Bedrock. See [Bedrock and fallback](/endpoint-compatibility#bedrock-and-fallback).

## Dispatch diagnostics (1.3.1)

Native Bedrock dispatch failures raise `DispatchError`, available from `rbtrace`.
Its diagnostic fields contain no credentials, request bodies, server response
bodies or raw exception text:

| Field | Meaning |
| --- | --- |
| `category` | A fixed classification such as `authentication_failed`, `permission_denied`, `timeout`, `transport_error`, `conflict` or `service_error` |
| `status_code` | HTTP status when available; otherwise `None` |
| `dispatch_id` | Generated UUID identifying this dispatch |
| `outcome_unknown` | `True` on a dispatch error; the diagnostics do not prove that a run is inactive elsewhere |
| `retry_safe` | `False`; the error does not authorize a retry or AWS fallback |

`rb.diagnostics()["last_dispatch"]` is `None` before a dispatch completes.
Afterwards it holds the most recently completed dispatch's `dispatch_id`,
`elapsed_ms`, `route`, `category`, `status_code`, `outcome_unknown` and `retry_safe`.
A confirmed `route` is `upstream` or `candidate`; on failure it is `None` and
`category` explains the failure. Only one record is retained. For concurrent
calls, use the caught error's `dispatch_id` to identify that call.

`elapsed_ms` measures the dispatch request, including endpoint discovery if needed.
It excludes the subsequent AWS operation and capture upload. `rb.status()` reads
remote recording status separately.

Reconcile an unknown outcome before retrying model work. Do not automatically
replay through AWS, create another dispatch ID, or treat an HTTP error as proof
that no candidate run exists. Only an explicit upstream decision permits the
SDK to invoke the original Bedrock operation.

## Server credentials

Use **API Keys** or **Data → Manage connection** to issue an `rb_live_` key.
Choose Capture, Inference, or both permissions; optional source binding applies
to both capabilities. Leave expiration empty for no scheduled expiration.
Existing keys retain their original permissions and expiry. An `rb_live_` prefix
alone does not guarantee Capture permission.

Legacy `rbcap_` source credentials retain source capture and existing proxy
rollout access until their configured expiry or revocation. Newly generated source credentials are persistent by default.
Rotation accepts the old source key for up to 24 hours, never beyond its expiry.
Revocation removes source-key access without waiting for that overlap.

## Source status

`GET /capture/SOURCE_ID/status` authenticates with `x-reasonblocks-key`.
The dashboard uses the signed-in session at
`GET /api/data-sources/SOURCE_ID/connection-status`; it does not store your server key.

The response reports `status` (`waiting`, `connected`, or `attention`),
`recorded_requests`, `training_examples`, `excluded_requests`, `failed_requests`,
`last_recorded_at`, `last_error`, `exclusions`, `key_expires_at` and `expires_soon`.
An exclusion describes training eligibility separately from recording and provider
success. The dashboard refreshes these fields automatically while the panel is open.
`connected` is a capture status, not a trained-model or approval status. Training
preparation, budget approval, training and evaluation are separate steps.
The SDK status checks the credential used for that request. The dashboard shows
the last recorded connection credential's expiration; before the first recording,
it uses the legacy source key's expiration when one exists. Check **API Keys**
for every server key's current expiration and revocation status.

## Recorded exchanges

Use your signed-in session for these management endpoints. A server capture key
does not grant access to browse the source's stored exchanges.

`GET /api/data-sources/SOURCE_ID/recordings?offset=0` returns up to 50 recent
completed recordings, newest first. The recent index holds at most 256 entries.
The response has this structure:

```json
{
  "recordings": [
    {
      "id": "RECORDING_ID",
      "at": "2026-09-26T00:00:00+00:00",
      "recorded": true,
      "training_eligible": false,
      "reason": "thinking_not_trainable"
    }
  ],
  "total": 1,
  "recorded_requests": 1,
  "recent_only": true
}
```

`total` counts the recent entries available to paginate. `recorded_requests` is
the cumulative number of recorded exchanges and can exceed `total`. Pass a new
`offset` to read the next page; this endpoint does not enumerate the full archive.

`GET /api/data-sources/SOURCE_ID/recordings/RECORDING_ID` returns a completed
exchange by its stable ID. It can retrieve an older stored exchange after that
entry leaves the recent index. Index eviction does not delete the exchange or
stop new capture. These endpoints do not promise unlimited retention.

Each serialized backend exchange has a 4 MiB limit. The native SDK and public
HTTP gateway apply a smaller 2 MiB request limit. Privacy filtering and response
completeness also determine whether an exchange can be stored. Native partial
streams do not upload a complete event; inspect `rb.diagnostics()` for local
delivery failures even when remote status has no new recording.

The existing limit of 512 normalized training examples per source still applies.
Continuous exchange recording is separate from training admission: recording more
exchanges does not increase that training limit.

Recording IDs have durable private receipts so a completed upload can be
recognized after it leaves the recent index. A pending or uncertain ID requires
reconciliation. Do not create another ID or repeat a provider call merely because
an upload timed out or the ID is absent from the recent list.

## Environment variables

| Name | Purpose |
| --- | --- |
| `REASONBLOCKS_API_KEY` | Server key used by `Connection`; requires Capture permission for recording |
| `REASONBLOCKS_CAPTURE_KEY` | Dashboard-issued source capture key, supplied at runtime |
| `RB_CAPTURE_KEY` | Existing alias; if both names are set, their values must agree |
| `OPENAI_API_KEY` / `ANTHROPIC_API_KEY` | Your normal provider credential, read by the provider client as before |
| `REASONBLOCKS_CAPTURE_URL` | Shell variable used in the setup examples to pass the exact source URL to the CLI |
| `RBTRACE_DISABLE` | `1` turns run labelling off at startup; `doctor` reports that condition |
| `RBTRACE_HOSTS` | Optional extra hosts to label, comma-separated. A plain hostname matches only that exact host; a leading-dot entry such as `.example.com` matches its subdomains; `*` matches every host. The helper adds the configured capture hostname itself |

Keys do not belong in generated files or CLI arguments. New keys are persistent
unless an expiration is selected. Existing keys retain their expiration. Source-key
rotation provides a 24-hour overlap, bounded by the previous key's expiry.

## `client_kwargs()`

Returns client settings containing the configured `base_url`, `default_headers`
with `x-reasonblocks-key`, and `max_retries=0`. Pass them to the existing OpenAI
or Anthropic Python client constructor. Async clients accept the same settings.
Preserve other application settings and merge headers deliberately.

```python
client = OpenAI(**reasonblocks_setup.client_kwargs())
```

`max_retries=0` disables the SDK's automatic retries. A timeout can leave paid
work with an unknown outcome, because the provider may already have accepted the
request; a silent retry would repeat it. Reconcile that outcome before retrying.
An application with its own reconciliation policy can override `max_retries`
explicitly in the returned dictionary.

## Run labelling (automatic)

Importing the generated helper installs run labelling for the process: every model call
the provider client makes carries `x-rb-run` (which task) and `x-rb-seq` (call number
within the task). The dashboard groups a task's calls by `x-rb-run` and, with
`x-rb-snapshot-id`, uses that group for full-agent training. The sequence number is
carried on every call so a task's calls stay in order; the dashboard does not
currently read it and groups solely by `x-rb-run`. The labelling
patches only the HTTP transport the SDK uses, reads no bodies and sends nothing of its
own. It applies to allowlisted hosts; the helper adds the configured capture hostname
to the allowlist, and `RBTRACE_HOSTS` extends it as described above.
`RBTRACE_DISABLE=1` turns it off; `python -m rbtrace doctor` reports whether calls
from an environment will be labelled.

Without a named task the helper uses one process-wide run ID. That is correct for a
process that handles exactly one task; any process that handles more than one task
must name each task with `run_headers()` or an explicit `rbtrace.client.run()` scope.

## `run_headers(snapshot_id=None, run_id=None)`

Returns headers naming one task; if `run_id` is omitted, generates a new ID. Call once
per task and reuse the result as `extra_headers` on every model call of that task.
Required for any long-lived or multi-task process (queue worker, web server, batch
loop); unnecessary only when a process runs a single task. Sequence numbers are still
added automatically, keyed by the run ID.

```python
headers = reasonblocks_setup.run_headers()
```

| Header | Requirement |
| --- | --- |
| `x-rb-run` | One ID per task, retained through all its model calls; the dashboard's grouping key |
| `x-rb-seq` | Added automatically: 1, 2, 3 … within the task, so a task's calls stay in order. Not currently read by the dashboard, which groups by `x-rb-run` |
| `x-rb-snapshot-id` | Included when a real starting snapshot ID is supplied; needed for full-agent training, optional for ordinary capture. Must be 1–128 letters, numbers, underscores, periods, colons or hyphens — a malformed value is rejected, not ignored |

Legacy response headers may describe preliminary training admission. Prefer
`rb.status()` or **Manage connection** for completed recording and eligibility,
including streams that fail after their response headers have been sent.

IDs use 1–128 letters, numbers, underscores, periods, colons or hyphens. Header names
are case-insensitive: `X-RB-Run` / `X-RB-Seq` (as the shim writes them) and
`x-rb-run` / `x-rb-seq` are the same headers. The helper attaches identifiers; it does
not reset tools or create snapshots.

## CLI checks and migration

`python -m rbtrace doctor --path . --json` inspects local configuration, the Python
version, SDK availability, whether the selected SDK's HTTP transport can be
labelled, capture-key presence and the task-header contract. It makes no network
calls and does not validate provider credentials or prove capture delivery. Use
the helper's actual directory for `--path`.

`python -m rbtrace migrate` converts an older generated gateway connection when
given a real dashboard capture URL, and upgrades an unmodified generated `1.1.0`
connection to the current helper when given its existing URL. It backs up the
original files under `.reasonblocks/backups/` first. See
[migration](/agent-setup#migrate-an-older-generated-connection) for backup
behavior, customized helpers and the required application changes.
